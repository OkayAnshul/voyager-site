How Voyager was built

A one-person Android project, built in the open over roughly a year — including one deliberate architectural U-turn, a disciplined "verify-then-flagship" process, and a habit of grading its own work honestly.

Aug 2025 · Foundation

Privacy-first from the first commit

The earliest commits laid a clean-architecture skeleton with dependency injection, the core domain models, and a database encrypted from day one — encryption was an architectural decision, not a later bolt-on. The capture layer arrived quickly too: a foreground service, adaptive sampling, a boot receiver, and early multi-sensor capture. The bug-fix commits from this era are telling — zero-duration visits, GPS spam, Doze kills — the unglamorous realities of always-on Android location work, met head-on.

Sep–Dec 2025 · Maturation & a hard look

Repositories, analytics — and an honest retrospective

Repository implementations, analytics rollups, a search schema, and the first real use-cases landed. Then something unusual for a solo project: a wave of self-audit documentation that graded the codebase candidly — including its weakest axis, testing — and a dedicated phase attacking battery and performance. Naming the problems out loud set up the biggest decision of the project.

Mar 2026 · The rewrite

From "visit-first" to a "stream-first" pipeline

The first engine was visit-first: detect stops, then guess the movement between them. That made the live UI laggy and made gaps and transport-mode changes hard to reason about. The retrospective concluded the foundation wouldn't scale for the thing that mattered most — explainability. So the engine was rebuilt stream-first: a single, serial, explainable pipeline over the raw sample stream, with a gap watchdog and crash recovery. This is the architectural spine that makes "honest gaps" and per-row evidence possible.

Apr–May 2026 · Productization

A product, and a migration wedge

Build flavors, a mileage subsystem, photo day-stories, trip detection, a carbon engine — and a deliberate go-to-market wedge: a Google Timeline importer, for the people whose cloud Timeline was discontinued with no way out. "Lost your Timeline? Bring it home."

May–Jun 2026 · Hardening in waves

Verify on real travel, then raise to the flagship bar

The most distinctive part of the process. A single living catalogue drove the work in waves ordered by real-world impact — "does tracking even run?" before "polish." Every feature carried two gates: verified (behaves correctly on a real travel-test) and improved (raised to a written flagship bar). "A feature isn't done until both boxes are ticked." Each card specified exactly how to travel-test it and the bar it had to clear — and this is where the timeline-correctness work, the fitness subsystem, and the trust fixes were driven to done.

Jul 2026 · Publishing polish

The final pre-launch pass

A deep correctness audit — establishing a green baseline, then tracing the core logic for nullability, rounding, timezone math, and swallowed exceptions. It removed the last unsafe null-assertion, fixed place naming so no "Unknown place" reaches the timeline, and — because the app is pre-production — collapsed the throwaway migration chain to a clean baseline. Then, for launch, every feature was made free while the billing layer stayed dormant for a possible future.

The method, in one loop

The engine didn't get good by accident. Work was ordered by real travel-test impact, not by code domain. Each feature had to first be verified on an actual real-world test, then improved to a written "flagship bar" — and wasn't considered done until both were true. That single discipline is why the correctness work is deep rather than cosmetic.

Process signals

  • Conventional Commits throughout — a legible history across 200+ commits, with a dedicated scope for the feature catalogue.
  • Docs coupled to code — feature commits land with their catalogue update, so the documentation never drifts from what actually shipped.
  • A written bar per feature, and a habit of testing on real travel — not just unit tests.
  • CI on every change — per-flavor tests, both-flavor assembly, lint, and a monthly dependency-security scan. A test even fails the build if the architecture's layers leak into each other.
  • The willingness to make a hard call — the visit-first → stream-first rewrite — when the retrospective said the foundation wouldn't scale.

A note on honesty: Voyager is a transparent heuristic engine, not an ML one, and it's pre-production — no real users yet, so any performance figures are rigorous estimates, not field data. It was built with AI pair-programming; the architecture, the decisions, and the product direction are the developer's own.
